The Chat Application is designed around a User, Chat, and Message model. We create a User class to maintain user details such as user ID and name, and a Message class to store the message ID, sender, content, and timestamp. We define a common Chat interface that is implemented by OneToOneChat and GroupChat, allowing us to support both individual and group conversations through polymorphism. A one-to-one chat contains exactly two participants, whereas a group chat supports multiple participants along with additional functionality such as a group name, admin, and adding or removing members. To avoid duplicating common functionality, we introduce an AbstractChat class that maintains the chat ID, participant list, and message history, and provides common operations such as adding messages, retrieving messages, and checking whether a user belongs to the conversation. The ChatService acts as the central service responsible for creating conversations, retrieving chats, and sending messages. When a user sends a message, the service identifies the requested chat using its chat ID, validates that the sender is a participant, creates an immutable Message object, and adds it to that chat's message history. We also maintain a mapping of chat IDs to Chat objects so that users can retrieve all their conversations without storing separate chat objects inside every user. To prevent duplicate one-to-one conversations between the same pair of users, the service checks whether an existing conversation already exists before creating a new one. For group conversations, only the group admin can add or remove members, and membership validation ensures that only existing participants can send messages. We implement the Observer Pattern using a ChatObserver interface, with implementations such as MessageNotificationObserver, which notifies other participants whenever a message is sent, and ChatActivityObserver, which updates the latest activity of a conversation. Whenever a new message is added, the ChatService notifies all registered observers, allowing additional functionality such as push notifications, unread message counts, and activity tracking to be added without modifying the core messaging logic. We use synchronization around shared chat operations to maintain consistent message history and participant information when multiple threads access the same conversation. Overall, the design uses interfaces, inheritance, polymorphism, encapsulation, and the Observer Pattern to keep one-to-one and group messaging extensible while separating conversation management, message handling, and notification responsibilities.
