In the Amazon Locker system, we will have a LockerService that manages locker locations and slot allocation. Each LockerLocation will be associated with a ZIP code and contain multiple Locker units, and each locker will contain multiple LockerSlot compartments of different sizes, such as SMALL, MEDIUM, and LARGE, represented using an enum. When a customer places an order, the system will identify a suitable locker location using the ZIP code and then use a SlotAllocationStrategy to find an available slot based on the package size. Before assigning the slot, we will perform package size validation to ensure that the package fits inside the selected compartment. Once a suitable slot is found, it will be reserved so that another delivery request cannot assign the same slot concurrently. We will maintain the slot's status using states such as AVAILABLE, RESERVED, OCCUPIED, and OUT_OF_SERVICE. We can use the State Design Pattern to manage these states and define valid transitions, for example, an available slot can become reserved, a reserved slot can become occupied after successful delivery, and an occupied slot can become available after pickup. Once the slot is assigned, the delivery agent will be authorized to access it using a temporary deposit credential. The agent will open the slot, place the package inside, and close the compartment. After successful deposit, the slot status will change to OCCUPIED, and the system will generate a unique pickup OTP through the OTPService. This OTP will be associated with the package and its assigned slot, will have an expiration time, and will be valid for only one successful pickup. If the OTP expires, the customer will need to request a new one through the system. We will use the Observer Design Pattern to notify the customer when the package has been successfully deposited, sending the pickup OTP and locker location details through a notification observer. When the customer visits the locker location and enters the OTP, the system will validate the code, check its expiration and usage status, and open the corresponding slot if the verification succeeds. Once the customer collects the package and closes the compartment, the slot status will transition back to AVAILABLE, making it eligible for another assignment. We will use the Strategy Design Pattern for slot allocation so that we can support different allocation approaches, such as selecting the first available suitable slot or choosing the smallest available slot that can accommodate the package. Overall, the design uses State for slot lifecycle management, Observer for customer notifications, and Strategy for flexible slot allocation, along with OTP expiration, package-size validation, slot reservation, and concurrency handling to make the system reliable and extensible.
